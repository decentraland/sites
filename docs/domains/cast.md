# cast

LiveKit browser streaming. Absorbed from `decentraland/cast2`. Mounted under `<DappsShell />` (heavy route) with an extra `<CastLayout />` wrapper that provides LiveKit + Notification contexts and renders the toast stack.

## Routes

`/cast/s/:token`, `/cast/s/streaming`, `/cast/w/:worldName/parcel/:parcel`, `/cast/w/:location`. Plus `/cast` index and `/cast/*` catch-all rendering `CastNotFoundPage`.

## LiveKit deps

`livekit-client` and `@livekit/components-react` are the heaviest deps in the heavy chunk — they only load when a `/cast/*` route is navigated to.

**CSS gotcha:** `@livekit/components-styles` ships CSS. It MUST NOT live inside `manualChunks` in `vite.config.ts` — Vite would inject the stylesheet as render-blocking on every page. See skill `perf-tier`.

## Presentation composition

A presentation renders in one of two ways, depending on whether the presentation state carries `slide`.

- **v1 (no `slide`):** the `presentation-bot:*` participant publishes one composited tile. `ParticipantGrid` shows it and auto-expands it only on its first appearance (a ref latches per bot-presence cycle and resets when the bot leaves), so a tile the user picks is not snapped back to the bot on re-render. The streamer's `CameraOverlayHandle` sits over that tile's `<video>` with no camera preview.
- **v2 (`slide` present):** the streamer view, the `/cast` watcher, and Places `SceneLiveWatcher` (both modes; `SceneRoomMount` provides `NotificationProvider` + `PresentationProvider`) render `PresentationStage` instead. The watcher keeps showing it after the streamer leaves, because the bot outlives them.
- **Stage layers:** the slide PNG as an `<img>`; the playing or paused video over its `slideVideos[playingVideoIndex].geometry` rectangle; the `presenterIdentity` camera in a circle at `overlay`, only while that camera is published and unmuted. `ParticipantGrid` never shows a `presentation-video` tile.
- **Slide video playback:** a `'stream'` video is the bot's `presentation-video` track and renders only while that track exists. A `'client'` video is played by `ClientVideo` from the parsed URL (`toClientPlayerSource` in `cast2.clientVideo.ts`), with no track: YouTube through the IFrame Player API (`youtubePlayer.ts`, script injected once on demand with a load timeout, skipped when the page already has the API, and chained onto any existing `onYouTubeIframeAPIReady`) in a self-created `credentialless` iframe so it embeds under the `Cross-Origin-Embedder-Policy: credentialless` that Places serves (a cross-origin frame with no COEP of its own is blocked otherwise), a Drive file in `<video>` from the presenter server's relay, `<PRESENTER_SERVER_URL>/api/drive-video?fileId=<id>` (Drive rejects browsers' cross-site media requests with a 403), and a Vimeo `.m3u8` in `<video>`, natively or through a lazily imported `hls.js` (`hlsSource.ts`). A URL that is not one of the three canonical forms renders no player and logs nothing. These failures remove the player, leave the black region, and log `[presentation] client video failed` with the player kind: the IFrame API script failing to load, the YouTube player constructor throwing, a YouTube player error, a `<video>` media error, a `play()` rejection other than `NotAllowedError` or `AbortError`, the `hls.js` dynamic import failing, a browser with neither native HLS nor `hls.js` support, and a fatal `hls.js` error that one `startLoad()` (network) or `recoverMediaError()` (media) attempt could not clear. A `<video>` play refused while already muted no longer removes the player: it keeps the muted player with its **Click to unmute** button, matching the YouTube path. The YouTube player runs without controls, keyboard shortcuts, fullscreen, other channels' related videos, annotations or captions; it clears the captions track on every API change, which also hides captions for viewers whose YouTube caption preference is on. The YouTube logo, the title shown at the start and ads cannot be removed from an embed. The YouTube container is `inert`, so keyboard focus never enters the iframe. The player is keyed by index and URL, so a new video or `idle` remounts or removes it.
- **Client video sync:** the target is `videoPositionMs + (Date.now() − videoPositionAt)` while playing and `videoPositionMs` while paused, clamped to the duration when known. `videoPositionAt` is the presenter server's clock; a viewer whose wall clock is more than the 2 s tolerance off the server stays that far off, because `videoPositionAt` also encodes how long ago the anchor was set, so it cannot be replaced by the local receipt clock without breaking late joiners' extrapolation. Correcting the skew needs a server clock reading per packet (a `serverNow` the server does not send today) — a known limitation, not a client-only fix. `ClientVideo` checks the target when the player is ready, on every position or state change, and every 5 s while playing. It seeks only when more than 2 s off and not seeking or buffering, then plays or pauses to match. A video that ends locally holds its last frame until the presenter moves the position to before its end, which clears the ended latch and resyncs it. The player follows the tab mute. On the first refused play attempt, the player mutes and shows a **Click to unmute** button, and it retries playing only while the state is still `playing`; a paused video stays paused until the presenter resumes. Later refusals change nothing, and the 5 s sync tick makes the next attempt. A YouTube refusal never removes the player: YouTube's event does not say which request it refuses, so the adapter reports no mute state, and the player stays muted with the button showing. The button is the only part of the region that takes pointer events, and it sits above the camera bubble and the presenter's drag handle. It is never wider than the region, and the region does not clip it, so it stays visible in a short region. The YouTube adapter reports `isPlaying()` from a `play()` request until the player settles, so a sync pass does not repeat a pending `play()` request.
- **Who controls the bubble:** `controllableOverlay` (`cast2.overlay.ts`) decides for both the drag handle and the camera dropdown's size/corner options. `state.overlay` is `null` when the server sends no `overlay` (the presenter server before client composition, which neither applies `presentation:overlay:update` nor draws a bubble), and then nobody gets the controls. Otherwise v1 gives them to any streamer with the camera on, and v2 only to the `presenterIdentity` participant, because the server applies overlay updates from any sender. A packet with no `overlay` during the 1 s local hold keeps the local layout.
- **Presenter handle:** only the `presenterIdentity` participant gets `CameraOverlayHandle`. It draws their local camera, mirrored, inside the dotted circle, so dragging has no server round-trip, and the stage leaves its own circle out for them.
- **Slide origin:** the stage sets `<img src>` only when `isAllowedSlideUrl` (`src/features/cast2/cast2.slideUrl.ts`) accepts the URL: the `getPresenterServerUrl()` origin and a `/presentations/<uuid>/slides/<16 hex>.png` path, the exact shape the presenter server issues.
- **Bot trust:** `PresentationContext` follows one bot: the first `presentation-bot:*` participant whose metadata has `role: 'presentation'`, or else the first `presentation-bot:*` participant, so packets that beat the metadata update are not lost. Presentation packets from any other sender, a second bot included, are dropped. Bot metadata and `presentation:state` packets go through one parser (`toIncomingState`) that defaults bad fields instead of rejecting the message: an unknown `videoState` (the server's `'error'` included) becomes `'idle'`, so the play control stays available. Slide videos are all-or-nothing on shape only (string `url`, finite geometry), and each entry's `source` is `'client'` only on an exact match, else `'stream'` (older servers send none); geometry is not range-checked because `playingVideoIndex` indexes the server's list and the PPTX renderer can emit off-slide or zero-size rectangles.
- **Camera bubble drag:** `useNormalizedPointerDrag` cancels a press when a move arrives with `buttons === 0`. Keep that guard: the `HandleCircle` can unmount or lose capture mid-drag (a remeasure, the circle dropping under `MIN_CIRCLE_DIAMETER`, a v1/v2 switch) with no `pointerup`/`pointercancel`, and without it the next plain hover keeps dragging the bubble and sends overlay commands.
- **Protocol:** the field contract is "Shared protocol contract" in `cast-presenter-server/docs/specs/client-composition/plan.md`, and for `source`, `videoPositionMs`, and `videoPositionAt`, "Shared protocol contract" in the server's `client-played-videos` spec.

## Auth

Cast can run anonymously OR with a token-in-URL. The `cast2Client` baseQuery handles both shapes. See skill `auth-flow` for the localStorage wallet hooks (only used when a logged-in user joins).
